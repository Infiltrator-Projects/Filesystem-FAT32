# FAT32 original-format technical reference

## Historical development and compatibility

This integrated reference describes native media structures, historical compatibility profiles and independent implementation requirements. The cited original specifications remain authoritative.

FAT evolved from Microsoft's 8-bit design (1977-78), QDOS FAT12 (1980), PC DOS/MS-DOS FAT16 (1984), and Compaq FAT16B (1987). FAT32 debuted in Windows 95 OSR2 / MS-DOS 7.1 in August 1996. It grew the allocation namespace while retaining the classic 32-byte directory entry and VFAT extension. Windows 98 offered FAT16-to-FAT32 conversion; Windows 2000 added native FAT32 support to the NT line; Winternals provided a separate NT4 driver. Caldera DRFAT32 (1998), DR-DOS 7.04 and IBM PC DOS 7.1 (1999) are historical implementations. MBR 0x0B is conventional FAT32 and 0x0C is LBA FAT32 (FAT32X). Do not use CHS hints as authoritative LBA geometry. Windows formatter limits (historically 32 GB in particular tools) are not the on-disk maximum. Windows 11 preview changes announced in 2024 are historical software-policy evidence, not proof of current provider capability.

## FAT32-specific boot parameter block

Offsets in the volume boot sector, hex offset:size in bytes, little-endian: 0x24:4 FATSz32; 0x28:2 ExtFlags; 0x2A:2 FSVer (0.0 for baseline); 0x2C:4 RootClus; 0x30:2 FSInfo sector; 0x32:2 BkBootSec; 0x34:12 reserved; 0x40:1 drive number; 0x41:1 reserved; 0x42:1 extended signature; 0x43:4 volume serial; 0x47:11 volume label; 0x52:8 type text. RootEntCnt, FATSz16 and TotSec16 must be zero in the conventional FAT32 BPB. ExtFlags bit 7 clear means mirror all FATs; set means low 4 bits select the active FAT. Check active index against NumFATs. RootClus is usually 2, not mandatory 2; traverse its chain like any directory. Reserved sectors commonly 32; FSInfo often 1 and backup boot 6. Derive locations from validated BPB, not constants. Some historical hybrid EBPBs and absent-FSInfo encodings are nonstandard and need separate qualification.

## FSInfo and backup structures

FAT32 FSInfo uses hex byte offsets 0x000:4 lead signature 0x41615252; 0x004:480 reserved; 0x1E4:4 structure signature 0x61417272; 0x1E8:4 free-cluster count; 0x1EC:4 next-free search hint; 0x1F0:12 reserved; 0x1FC:4 trail signature 0xAA550000. Unknown count/hint = 0xFFFFFFFF. Validate signatures, counts, hints and both FSInfo and backup boot addresses within reserved space; a valid hint is not allocation proof. On unclean shutdown or inconsistent FAT state rescan authoritative allocation. Preserve reserved bytes during normal updates; initialise as specified on format. The backup boot record is recovery evidence, not a second live transaction. Typical Microsoft backup sectors 6..8 include companion data; validate geometry and exact revision before restoring. FAT32's FSInfo is not used in FAT12/16 or exFAT; it is not a journal. Mirroring is controlled by ExtFlags as described in the BPB section.

## 28-bit links, volume and file bounds

FAT32 entry n is LE32 at 4*n; interpret low 28 bits. Update by preserving the existing high nibble: (old & 0xF0000000) | (next & 0x0FFFFFFF). Free=0; reserved=1; usual next=2..0x0FFFFFEF; reserved=0x0FFFFFF0..0x0FFFFFF6; bad=0x0FFFFFF7; EOC=0x0FFFFFF8..0x0FFFFFFF. FAT[0] low 28 bits carry media byte plus ones; FAT[1] bit 27 clean shutdown and bit 26 no I/O error, where supported. Classification starts at 65525 data clusters; avoid marker-valued cluster IDs and near-boundary geometry. The 32-bit sector count caps total size at (2^32-1)*sector_size: just under 2 TiB at 512 bytes or 16 TiB at 4096 bytes, with FAT capacity and cluster limits also enforced. Standard file-size maximum is 4,294,967,295 bytes. FAT32+ (2007 draft) repurposes reserved directory bits for larger lengths, up to 256 GiB-1; unqualified classic tools can truncate such files. It is not baseline FAT32 and may conflict with OS/2 FAT32.IFS EAs.

## Common BPB and region arithmetic

Hex byte offset:size (modern DOS/EFI layout): 0x00:3 jump; 0x03:8 OEM name; 0x0B:2 bytes/sector; 0x0D:1 sectors/cluster; 0x0E:2 reserved count; 0x10:1 FAT count; 0x11:2 root entries; 0x13:2 TotSec16; 0x15:1 media; 0x16:2 FATSz16; 0x18:2 sectors/track; 0x1A:2 heads; 0x1C:4 hidden sectors (DOS 3.31 layout); 0x20:4 TotSec32. Boot signature bytes 55 AA at 0x1FE. The Microsoft EFI profile specifies logical sector sizes 512, 1024, 2048 or 4096 bytes and sectors/cluster 1, 2, 4, 8, 16, 32, 64 or 128. For broad compatibility its cluster size must not exceed 32 KiB; larger or older nonstandard geometries need explicit profiles. FATSz32 must be nonzero and RootEntCnt zero. Use checked arithmetic. root_sectors=0; fat_sectors=FATSz32; total=TotSec32; first_data=reserved+FAT_count*fat_sectors; cluster_count=floor((total-first_data)/sectors_per_cluster). Reject overflow, underflow, truncated media and FAT capacity below cluster_count+2 entries. Cluster n sector=first_data+(n-2)*sectors_per_cluster, relative to volume; add partition offset only in whole-device host translation. CHS translation is historical: LBA=((cylinder*heads)+head)*sectors_per_track+sector-1. FAT type is based on count, not the textual label or partition ID. On GPT media the Microsoft basic data GUID is EBD0A0A2-B9E5-4433-87C0-68B6B72699C7; it is shared with other formats. Stay at least 16 clusters away from type cutovers when formatting for broad legacy compatibility.

### Worked FAT32 geometry

For 1048576 sectors of 512 bytes, eight sectors per cluster, 32 reserved sectors and two 1024-sector FATs, first data sector is 2080. Data cluster count is floor((1048576-2080)/8)=130812; FAT entry capacity=131072. Cluster 100 maps to sector 2864. Check root allocation, active FAT and address range separately before accepting the worked volume; use the BPB, classification and entry rules above.

## Directory record - exact 32-byte layout

Hex offset:size: 0x00:11 OEM short name (8 base + 3 extension, spaces padded); 0x0B:1 attributes; 0x0C:1 NT case flags (base lowercase bit3, extension bit4); 0x0D:1 create 10ms increment (0..199); 0x0E:2 create time; 0x10:2 create date; 0x12:2 last access date; 0x14:2 first-cluster high word on FAT32, reserved or historical EA handle on FAT12/16; 0x16:2 modification time; 0x18:2 modification date; 0x1A:2 first-cluster low word; 0x1C:4 file size. Attributes: 0x01 read-only, 0x02 hidden, 0x04 system, 0x08 volume, 0x10 directory, 0x20 archive; 0x0F identifies LFN; upper bits reserved. First byte 0x00 means end, 0xE5 deleted, 0x05 encodes initial OEM 0xE5. Directory sizes are normally zero in their entries; derive chain length by traversal. Microsoft specifies a maximum directory storage size of 2 MiB (65,536 records, not files); the fixed FAT12/16 root has a separate BPB-defined limit. Dot points to self; dot-dot uses zero for root parent. Root volume labels are metadata, not ordinary files. Timestamp date bits 0..4 day, 5..8 month, 9..15 year minus 1980; time bits 0..4 seconds/2, 5..10 minute, 11..15 hour. Representable years 1980..2107; historic DOS API often limited to 2099. Access date granularity one day; modification 2s; create increments 10ms where supported. No stored timezone in classic FAT. Preserve unknown/reserved fields as applicable to explicit profiles.

## VFAT long filenames and aliases

VFAT is an optional directory extension to FAT12/16/32, not a separate allocation format. Windows NT 3.5 and Windows 95 adopted long names. Each LFN entry: 0x00:1 ordinal (0x40 marks last logical fragment, physically first); 0x01:10 five UTF-16 units; 0x0B:1 attr=0x0F; 0x0C:1 type=0; 0x0D:1 short-name checksum; 0x0E:12 six units; 0x1A:2 zero first cluster; 0x1C:4 two units. At most 20 records and 255 code units, physical sequence descends to 1 then short entry. Partial final fragment ends with 0x0000 then 0xFFFF padding; full fragment need not include terminator. Checksum over all 11 padded short-name bytes: start s=0, for each b set s=((s>>1)|(s<<7))+b modulo 256. Validate ordinal, checksum, terminator, padding and UTF-16; if invalid, expose only valid short alias or fail according to corruption policy, never fabricate a long name. Alias generation and collision handling are implementation/OS-specific. Preserve associated LFN records through rename/delete and detect orphaned entries. Historical UCS-2 terminology differs from UTF-16 surrogate handling. Short-case bits do not encode arbitrary mixed case.

## Historical extensions, metadata and derivatives

Classic FAT has no native ACLs, resource forks, compression, encryption or general transaction journal. DR-DOS, FlexOS and related multiuser DOS products implemented security extensions; SuperStor, Stacker, DoubleSpace and DriveSpace historically supplied volume compression; DR-DOS supplied optional volume encryption. These are separate compatibility profiles, not baseline capabilities. OS/2 FAT12/16 stores EAs in hidden EA DATA. SF referenced by directory field 0x14; FAT32 uses that word for cluster high bits, so FAT32.IFS uses separate EA. SF sidecar files and marks at 0x0C instead. Macintosh PC Exchange used FINDER.DAT and RESOURCE.FRK; macOS uses AppleDouble ._ files and .DS_Store; UMSDOS used --linux-.---. These are host conventions, not native FAT streams. DELWATCH pending-delete and IBM 4680/4690 distribution attributes repurpose fields; avoid writing unknown extensions. Human68K 18.3 names, TFAT and OEM variable root variants require independent profiles. FATX (Xbox 2001) uses incompatible boot and 64-byte directory records; Turbo FAT is a NetWare derivative. FAT+ draft (2007) is not baseline FAT16/32. Do not claim support or silently reformat any of these formats.

## Allocation, recovery and qualification

No general journal: mirrored FAT copies are not proof of atomicity. Build a reference map from valid directory trees, follow bounded chains, compare expected ceil(file_size/cluster_size) to actual allocation, distinguish zero-length files and directories, detect cycles, cross-links, orphan clusters, bad markers and inconsistent mirrors. The namespace and relocation exercise below gives the durable mutation sequence. Never run recovery against a guessed target. Free-space scans are linear; allocation hints, contiguous reservation, caching and multi-sector I/O can reduce fragmentation and metadata reads. Slack is unused tail space inside allocated clusters, distinct from external fragmentation. Formatting must solve FAT capacity and root geometry together, not merely write a type string. Test exact boundary counts, sector straddles, odd/even links, malformed BPBs, directory capacity, LFN collisions and corruption, full disks, truncated media, I/O failures and interrupted relocation. Historical recovery and undelete (0xE5) cannot guarantee content remains intact.

### Namespace and relocation exercise

For a 10000-byte file with 4096-byte clusters, three clusters are required. Traverse its chain with range and cycle checks and reconstruct physical runs. Verify chain ownership across all directory entries, preserving long-name records and timestamps. Validate target identity and exact source bytes, reserve a new run, copy data and verify it, publish the new first cluster or predecessor link, flush, then retire old ownership. If the root or another directory moves, its parent reference and root BPB implications need special treatment. Inject interruption at each boundary and independently check the resulting image; the ordering is not a guarantee of crash-atomicity. Never treat a lost chain or conflicting FAT copy as permission to guess ownership.
